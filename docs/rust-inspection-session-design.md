## 已落地

Rust 保存捕获时的原图字节，返回带图像 ID、尺寸、内容 SHA、字节数及进程内 token 的不可变引用。前端以图像记录和资产身份缓存引用，后续节点及重复检测复用引用。Rust 原图注册表最多 16 项、128 MB；过期引用在执行程序前从原始来源重新校验、注册。

Rust/Python 常驻协议 v3 首次发送原图字节，Python 验证后保留不可变 bytes。后续只发送完整引用。每次回覆携带实际仍存活的 token，Rust 据此决定是否需要补发。进程退出或超时后，Rust 清除进程状态；新进程会重新接收原图。Python 原图缓存也限制为 16 项、128 MB，解码缓存保留原来的 8 项、128 MB 上限。

算法仍获得独立可修改的数组；SDK 的原图路径是每次调用独立写入的文件。算法写数组或覆盖自己的输入文件，不会污染缓存或其他调用。普通检测保留 SDK 路径兼容性，因此当前仍会产生输入原始文件；没有宣称已经消除所有磁盘访问。

前端历史快照共享经过 JSON 归一化并递归冻结的执行结果、程序追踪、结构图层及产物数据。解说修订、预览、路径和操作状态仍独立复制。普通读取继续返回独立可编辑副本。“另存为”按变更的分支复制资产路径，保留旧撤销快照的内容。注册原图的 token 存在前端 WeakMap 中，不加入持久化的算法记录。

当前 JS 准备所有节点请求，一次交给 Rust；Rust 连续执行，组装完整节点运行记录，并生成量测观测、分类、判定依据及完整工件记录，直接调用既有持久化服务，等待实际保存收据后返回。JS 与原生产实现逐项对照并采用原生记录及收据。以下是继续收敛的数据所有权目标，其中连续执行、进度、取消、原生决策和原生直接提交已落地；编译方案注册及按需返回完整事实仍需继续收敛。

1. 注册编译方案。前端提交已经验证的方案和身份；Rust 保存不可变定义与编译顺序，返回会话 token。token 绑定方案内容，不能仅凭调用者自报的指纹复用。
2. 执行工件。前端提交工件身份、原图资源引用、多视图映射、固定参考及调试策略。Rust 持有当前工件的 run map、节点状态和实际产物，连续执行节点。
3. 逐步报告。Rust 发送带会话 ID、工件 ID、运行 ID、单调序号的状态事件及预览引用。前端依身份检查后更新当前画面。界面事件处理不作为派发下一节点的前提。
4. 取消。前端取消命令针对会话 ID 设置原生取消标志；Rust 在节点边界检查。活动进程继续受原有超时监督。取消记录保留真实已执行节点，未执行节点有明确原因。终止决策在提交前确定；提交期间才到达的停止用于阻止下一件，不能重新标记已经提交的当前件。
5. 保存并确认。Rust 将实际运行事实和分类结果直接交给持久化服务，成功提交后返回收据。前端以保存收据和当前原图/结果图可见状态恢复控件。保存失败必须显示，不能提前结束计时。

完整追踪和 JSON 产物最终应由 Rust 持有。界面获得操作所需的节点摘要和引用；用户读取详细数据、历史记录、解说或询问时，按实际引用获取完整事实。当前节点图像仍留在内存。不得将普通读接口改成静默截断，也不得为了缩短关键路径丢弃历史或解除撤销能力。

## 必须先搬迁的语义

原生调度需要与现有 `workpiece-runner.js`、`workpiece-lifecycle.js` 和 `data-contract.js` 对齐：父子生命周期、分支条件、任一前提、正常未找到、故障、必需产物、坐标系、单位及实际数据格式。输出契约失败时，必须在下游使用该产物前阻断。前端收到全部结果后再发现错误，不能代替这一条件。

方案包含 Rust 原生节点和 Python 扩展节点时，使用同一状态机与记录结构。算法代码、参数、分类规则和节点实现保持原样。SDK 的用户回调时间继续计入算法；图像转换、追踪、验证和存储继续计入框架。

## 实施与验收顺序

先把现有纯函数的状态和契约检查搬到 Rust，并通过同一输入的 JS/Rust 差异检查固定语义。再拆分前端的请求准备与结果导入，接入一个工件的原生命令和状态事件。最后将记录事实直接交给原生保存，缩减跨桥的完整追踪数据。

随后用该次桌面记录的 10 个真实资产（共 702322 字节）做同进程交替对照，见 `framework-performance/artifacts/continuation-20261112-cas-comparison/validation-v2/verification.json`。复用已有资产的 48 对，生产串行 `store_asset` 平均 **17.550 ms**，生产 `queue_asset` 加有界并行 `flush_pending_assets` 平均 **12.911 ms**。首次创建资产的另外 48 对平均 **110.278 → 61.438 ms**。每次均独立逐字节回读全部文件；计时包括真实描述符/哈希、已有字节核对，新资产还包括 fsync 和原子重命名，排除回读判据、工件记录、日志、算法与界面。因此支持保留有界并行保存，但不能把这两个局部均值当作整件性能。

该诊断只临时追加 cfg(test) 测试模块，直接调用生产函数；编译源码、原始生产源码、测试模块、输入资产和日志均已保存。finally 移除准确的临时模块后，全部生产源文件再次与已验收桌面运行的哈希匹配，发布实现没有被基准测试替换。

“首次资产”指没有已有内容地址文件，不等同于 Python 进程冷启动。即使工作进程已经预热，新图或改变的 JSON 产物也可能支付这项成本。当前试验下，仅此阶段的并行均值已经超过整件 50 ms 预算。后续需要探索将新资产按批次写入可校验的事务容器，减少逐文件同步和元数据操作；必须先证明原始字节、去重、损坏拒绝、保存失败传播、历史回读、另存为/导出及版本回滚仍正确，再接入生产。该事务容器尚未实现，不能计为收益。
