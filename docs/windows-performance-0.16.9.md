Windows 检测完整周期耗时报告（0.16.9）

2026-11-11；状态：**未达到 300 ms，不能按性能要求验收**。本次固定同图六轮真实桌面完整周期为 1112.0–1214.5 ms，中位数 1150.4 ms，约为 300 ms 目标的 3.83 倍。100 ms 为进一步目标，本次没有达到。

- CPU：Intel Core Ultra 9 185H，16 核、22 逻辑处理器。分析工具 Python 3.12.7、OpenCV 4.11.0、NumPy 2.4.4。CPU 占用、温度、功耗、线程调度未录制，不能据此把剩余差距归因于机器性能或系统调度。
- 原图 1280×1024，同一图片身份 SHA 为 6b0f6432a1d55777711a8780ea9dd75b5984ae9c3b22944cf187a431ad910f46。历史导出中的文件内容 SHA 为 3acedf2878d93ee0e76c7ab679272beace6cdc0d6cb4177fa83f6dfa4707a337；两种 SHA 的定义不同，不直接混用。
- 固定同一张图、自动切换关闭、常驻 Python 已热启动、保留主界面输入原图与本次输出内存图、关闭阶段 PNG 保存。另行测过自动切换两个入口、调试保存、停止和 33 张原图。
- 开始：点击“执行一次”前。结束：结果保存完成、按钮可用、当前节点输出与输入均解码且可见，再等待两个界面帧。300 ms 不偷换成某个节点时间。切换打开时应额外计入换图；本表未将其混入同图基准。
- 六轮全部热跑；0.16.8 基线热跑约 3788–3845 ms，历史首次运行较慢。上一轮“按钮可用”的计时与这次“图也可见”边界不同，因此只作改善参考，不按精确同比百分比宣传。

**完整周期分解**

| Rust 执行器其余工作（原生总耗时减 Python） | 230.0 | 19.9% |

三节点 Python 本体合计已经超过 300 ms。即使将所有桥传输、保存和界面耗时降到零，当前算法实现仍不能满足完整周期 300 ms。

**已证实的慢点及已做的修复**

1. 原先在正常检测中写阶段 PNG、重复大报告、图像 Base64 和 JSON 的路径产生大量额外工作。正常检查现改为：只向下游提供需要的原始 raster；主输出通过常驻进程二进制帧返回宿主，在 WebView 中以内存 BMP 显示；临时 JSON 和检查历史不保存主输出像素。打开调试才保存阶段 PNG。本次正常记录 storedPixels=0；调试保存的 5 张 PNG 均可从记录重新读取，哈希与 0.16.8 基线一致。
2. 原歪斜方案存在 Python 半径网格循环、候选组合和重复外缘计算。已做 NumPy 批量计算、扫描峰值向量化、外缘复用；保持搜索网格、候选数量、阈值与判定规则。常规记录保留结果和候选摘要，逐半径诊断只在调试时输出。优化版位于独立工程副本，打开原工程仍执行原工程的算法代码。
3. 常驻 Python 已启用；热跑 receipt 的 coldStart=false，不能继续把热跑的大头说成“每次启动 Python”。原图解码缓存也已命中。Windows Python、Agent、Git 子进程统一隐藏控制台；本次窗口事件监听未发现黑窗。
4. 界面回归已修复：左侧直接读取当前原图，右侧使用当前工件的内存图；连续运行时输入跟随执行工件，换图不再提前清除唯一的当前工件缓存。引用 BMP 时只在用户主动询问时转为讨论支持的 PNG，不在普通检测过程中存 PNG。
5. 自动切换失效的直接原因是三个入口写死 autoAdvance=false。主工具栏、图像源弹窗和画布图像源入口现遵从保存的自动切换开关。自动切换只准备下一张，不自行启动下一次检测。实测覆盖主工具栏和图像源弹窗；关闭开关的六轮同图基准没有换图。

**优化后算法函数剖析**

另外对同图优化版歪斜代码运行 cProfile，输出见 optimized-objects-profile.txt。该剖析会增加 Python 调用开销，而且沿用历史请求的输入路径；只用于函数归因，不作为完整桌面耗时或节点性能验收值。

- profile 中 scan：3 次，累计约 101 ms，包含 958 次 OpenCV remap 中的一部分。
- coherent_candidate：15 次，累计约 107 ms；fit_radius：30 次，累计约 67 ms；candidate_edges：12 次，累计约 19 ms。
- save_json：5 次，累计约 69 ms；json_value 递归约 7 万次，累计约 56 ms。普通模式仍有结构化结果和依据信息需要构造、验证和保存。
- 这些是包含子调用的累计时间，**不能相加**；用于确定候选生成、半径评分、结构数据生产的下一步优化点。当前版本未直接减少候选或抽稀搜索来追求数字。

**仍需修正的架构开销**

- 目前三个节点仍分别从 JS 调到 Rust，再进入同一个 Python worker，每个节点都写请求／报告，宿主再读回、核验并返回。常驻解释器解决了启动成本，未解决每节点的文件往返和桥协议开销。
- 主输出虽不落盘，Rust→WebView 仍经 BMP 的 Base64 JSON 传递。1280×1024 的 24 位 BMP 约 3.93 MB，Base64 约 5.24 MB；三张约 15.7 MB。这是按尺寸推导的传输量级，不是网络抓包结论；本次未改成有界二进制内存资源协议。
- 报告和依据数据存在跨层复制、哈希、转换和逐字段核验。省掉 PNG 后，这部分和重复文件读写仍占明显比例。不能为降低时间而跳过结果真实性核验或假装保存完成。
- 结果保存与 UI 重建仍位于完整周期内；实测必须将其计入，不能只报告 Python 算法耗时。

**下一步实施与验收顺序**

| 改动 | 作用 | 必须保留的验收 |
| --- | --- | --- |
| 一次下发完整编译方案，由 worker 内串联节点与内存数组 | 消除三次桥往返和 shared_gray 临时文件 | 图与参数身份一致，节点状态、取消边界和故障可追踪 |

这些是后续工程方案，**尚未实现或承诺提速比例**。本次保留所有必要功能后仍有上述时间，故明确判为性能未达标，不能声称恢复到 300 ms。
