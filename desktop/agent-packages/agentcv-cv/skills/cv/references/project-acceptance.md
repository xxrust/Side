# 真實項目的驗收與回歸

接手項目、調參或處理失敗案例時，先 `get_project_acceptance`。這是已保存的項目約定、固定樣本與實算索引；不要自行建立另一份「通過清單」。

## 約定與缺項

- 核對工件單位、輸入槽與固定參考；多相機是同件的 views，不是把整個資料集合成一次輸入。
- 分類與規則沿用 `get_purpose_scheme` 的 classificationSpec。量測找不到依規則分類，程序異常則走 FAULT；缺測處理與故障處置分別向工程師確認。
- `questions` 中缺少的漏檢、誤剔、分類不一致、故障率與完整主機週期預算，應主動在當前對話詢問。可先做不依賴答案的算法工作。不能因示例恰好全對便自行填 0%，不能把算子時間當完整週期。
- `propose_project_acceptance(draft_json)` 保存完整草案及來源：比例使用 0–1；maxCycleMs 為毫秒。草案不是確認，面板「我確認這份約定」由人類操作。工程師回答後應更新草案，不能只回覆收到。分類規格的修改仍走正式方案工具；既有諮詢卡回答仍用 apply_canvas_consultation。

## 固定開發集與保留驗收集

- 人類在「分類與驗收規格 → 基準圖片」分配圖片、批次／實物分組、現場條件與人工答案，再固定集合。分組資訊不可由檔名推定；缺答案的集合可以開發試跑，但不能驗收通過。
- 固定清單含原圖與參考圖指紋、當時人工答案及來源、輸入／分類契約和建立時方案版本。調參不會覆蓋答案。重跑用 `run_acceptance_baseline`，不能自己拼一份只含容易樣本的 units 冒稱全基準。
- 平台阻止相同內容、同組工件跨集合；它不能自動認出所有近重複圖或判斷現場代表性。應請工程師核對批次、邊界、反例、遮擋、失焦、光照變化等實際條件。
- 保留集由人類面板啟動。這是工作流隔離，不是圖像存取權限沙箱。圖片若已參與開發／被查看，不宣稱盲測；若根據驗收結果調參，下次獨立驗收須補充未參與開發的樣本。

## 失敗案例閉環

1. 統計異常或回歸對比中的「交給 Pi 分析」建立固定案例。用 `get_project_acceptance(case_id)` 取得 executionId、unitId、schemeFingerprint、當時結果、recordRef 與方案快照；歷史方案不可用現在程式替代。
2. 有 recordRef 時 `get_inspection_unit` 讀實際保存結果；按需讀原圖、關鍵結果、當時參數與程式。若舊紀錄缺少完整方案快照，要明示缺失，不能補猜。
3. 修改後重跑同一固定開發基準，用 `compare_acceptance_runs(before_id,after_id)` 查看修復、新退步、未解決與時間變化。沒有基準先請人類固定；只修好眼前一張不等於完成。
4. 工具返回 INCOMPLETE、缺分母、FAULT、取消或超時不能寫成通過。漏檢是壞品被判良品，誤剔是良品被判壞品；多類分檔另看分類不一致率及統計中的逐類召回。缺故障資料不等於故障率零。

固定樣本全部通過僅是這些樣本的觀察結果，不代表量產能力。重複跑同一批圖可驗證穩定性與性能，不能增加獨立驗收樣本數。保留全部失敗與新退步，讓工程師決定下一輪資料與驗收。
